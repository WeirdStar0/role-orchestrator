# v0.1.1 补丁批次报告（V0.1.1-BATCH）

## 1. 根因

用户实测(v0.1.0 发布后):桌面壳首启页面报 **no such table: executions**。

- v0.1.0 的 serve 独立进程入口(`packages/local-api/src/serve.ts`,`runServe`)
  只调 `openDatabase`(`packages/store/src/connection.ts:32`:仅开库 +
  PRAGMA foreign_keys/busy_timeout/journal_mode/synchronous,**不建表**);
- 产品 schema 由 `@role-orchestrator/expand` 的
  `applyControlledExpansionMigrations(db, { now })` 建立
  (`packages/expand/src/controlled.ts:453`,迁移链
  `CONTROLLED_EXPANSION_MIGRATIONS` = 001..013 + 015 + 016 + 017 共 16 条,
  幂等,空库可跑;browser-e2e world.ts:114 即组合根用法);
- serve 入口漏调 ⇒ 壳以默认路径 `%LOCALAPPDATA%\role-orchestrator\orchestrator.db`
  首启时得到一个**零表**库,任何读业务表的 API/页面即抛
  `no such table`。

**教训(M8-05 冒烟六断言的盲区)**:v0.1.0 的 serve-bundle 冒烟
(`packages/local-api/test/serve-bundle.test.ts:122`)六断言——页面 200 →
无凭据 `/api/v1/session` 403 → 令牌文件 Bearer 200 → kill 有界退出且
stderr 空 → 坏 db 路径 fail-closed 非零退出 → bundle 缺失显式跳过——其中
**唯一带凭据的 200 探针是不读任何业务表的 `/api/v1/session`**,故零表库
照样全绿。本批补上的断言改为「带凭据 + 读业务表(经
`getRunDetail` → `listExecutionsForRun`,`server.ts:491`/`views.ts:132`
恰读 executions)」的探针,盲区闭合。
